# GPSH

The visible name is getodoo.sh (`product_name()` / `product_text()` / `product_description()` / `product_og_image_url()`). Models, routes, and tables stay Coolify names. Do not show Coolify or Odoo.sh in client-facing copy. Link previews (WhatsApp/OG) come from `resources/views/layouts/base.blade.php` and `public/brand/og.png` — never `cdn.coollabs.io` or coolify.io.

The product contract is the phases below. Long form: `docs/gpsh-architecture.md`, `docs/gpsh-odoo-phase-1.md`, `docs/gpsh-odoo-phase-2.md`, `docs/gpsh-odoo-phases-3-10.md`, `docs/gpsh-odoo-architecture-decision.md`. `docs/v5/` (coold, flux) is not this runtime.

Before changing launch, a project screen, GitHub, or Odoo: check the phase that owns that screen. If the UI still looks like stock Coolify where a phase already defined the behavior, that is the bug. Do not add a second flow beside the phase.

The deployment experience to reach is getodoo.sh style: one project, production and staging, one Odoo per environment, a branch, and a public HTTPS link. The client does not manage a scattered list of Coolify services. That project screen is phase 6. Do not hide Coolify's own tools from the owner: adding servers, S3, and the cloud providers Coolify already has (Hetzner, Vultr, DigitalOcean, and the rest of the server create screen) stay available.

The owner runs the platform. Admin and member are client profiles. Their limits are specific and are set on the invitation, before the sign-in link, for admin and member: projects, environments, members, production branches, staging branches, and services. Admin also gets the GitHub account, `can_add_servers`, and `can_launch_on_instance_server`. Member also gets `odoo.*` abilities. Server flags stay off for a member. Only the owner can write those on the invite. An admin who invites someone does not grant servers. Members never gain server or S3 access. A member or admin can open the Odoo shell of a service on their team. They cannot open a server terminal. An admin's other terminals stay limited to instances they created or that were assigned to them. Do not replace Coolify roles with a new role system.

`App\Livewire\Project\Resource\Index` keeps resource lists in `protected` properties. Livewire drops them on the next request. `render()` reloads them from the public project and environment. An empty environment shows a one-click launch picker (`selectedService` + `launchService`) fed by `ServiceTemplateCatalog::launchOptions()` (Odoo first, then every visible catalog/custom template). It asks where to run: local only with permission, create a server when none exist, or which server when some exist; `serverId` defaults to the first allowed server. Choosing Odoo keeps the GitHub/`LaunchOdooProjectJob` path. Any other template creates the service from `ServiceTemplateCatalog::composeFor` and dispatches `StartService`. If GitHub is installed and the project still has no repository, launching Odoo creates the service and opens configuration with `launch=choose` (new vs existing repository, or Launch without GitHub) instead of starting containers. `github=0` from Launch without GitHub on the project page skips that choice and launches. If another Odoo service is already there on `launch=choose`, redirect straight to its configuration. Custom Compose templates are created/edited in Settings → Service templates (`ServiceTemplateCatalog::create` / `save` / `restore`; table `service_template_overrides` with `is_custom`, display meta, `is_visible`).

## Phase 0

Reuse Coolify. Do not build a second deploy engine, a second Git checkout, a second webhook, or a second user system.

- Odoo is a `Service` (template `odoo` + Postgres), started with `StartService`. Not an `Application` image build.
- Git source is `GithubApp`. Webhook stays `POST /source/github/events`.
- One `Application` marked `is_odoo_addons` per environment is how that webhook finds the branch (`SyncOdooAddonsJob` copies into `{serviceUuid}_odoo-extra-addons` and restarts only the Odoo container). Do not add `OdooGithubApp`. Do not create an extra Application in assign/launch on top of that one.
- Login OAuth (`OauthController`) does not list repositories.
- Do not call `ProvisionOdooEnvironment`.

## Phase 1 — profile and staging quota

- `odoo_profiles`: one row per project. `odoo_version` is 17, 18, 19, or 20. Enabling Odoo only saves the profile. It does not create an empty staging.
- Staging is an `Environment` named `staging` or `staging-N`. `production` is not staging. No `OdooStagingEnvironment` model.
- Quota is on the user, written only by the owner. Not the old project columns. `max_projects` is the ceiling. A second project is refused when that number is reached, even if environments or services still have room. One allowed project includes one instance, and that instance includes its production branch and its staging branch. Those two branches do not spend a second project and do not need spare `max_environments` or `max_services` to exist. Rule: `OdooStaging::canCreateStagingEnvironment()`. No profile or a member: no. Owner, or admin with a null limit: yes. Admin with a number: staging environments they created, under that number. Production does not count. Any admin on the team can finish a staging launch on a project they can use. The other admin's quota does not block it, and the overlay must reach Done.
- `Project::createNextStagingEnvironment()` is the only creator. Clone calls it. One new staging, never a second production. If `staging` exists, reuse it; the next is `staging-2`.
- A project without a profile stays production only.

## Phase 2 — what the user must see

GitHub is optional. `request_oauth_on_install` is false.

New project: pick any visible service from the catalog (search by name; the menu must not be clipped). Odoo is the recommended hook and asks version 17–20 and Connect GitHub; other templates launch with `StartService` after create. Skipping GitHub still creates the project. For Odoo, JupyterLab stays on and shows addon files. One folder: Odoo `/mnt/extra-addons`, Jupyter `/workspace/addons`.

Connect GitHub uses the existing GitHub App register. A row without `installation_id` is not connected. Do not ask for `app_id`, installation id, or the private key in the project form. The app name comes from instance settings (default `gpsh1`), stored on `team_user.github_app_id`. The screen shows that account's login and repositories, not a list of apps. The owner can switch the account. The manifest for this path asks `contents: write` and `administration: write`. A GitHub App created from Coolify's normal source screen stays read-only.

Already installed (`app_id`, `installation_id`, private key; `webhook_secret` is not required): do not send them to install the app or to "Install repositories". A project reuses the GitHub App installed on that project's team. Another team gets its own app, so one client does not see another's repositories. A system-wide app is not used for Odoo. When this team already has several installed apps and the user has not remembered one on `team_user.github_app_id`, the first app of this team is used. Do not create a second app for a launch on the same team. Ask: launch production on a new repository, or search an existing one (reuse the repository search, up to five pages). Then start containers and wait for HTTPS. Creating that repository runs inside `LaunchOdooProjectJob`, and the button returns to the project at once. Do not create the repository or clone it inside the Livewire request. A secondary GitHub limit is waited out in that job (`Retry-After`, at most 90 seconds, three tries). Remaining `0` still stops the launch. After the project has a repository, the GitHub panel shows that repository and branch; it does not ask again unless the connected app no longer matches `odoo_profiles.github_app_id`. A project launched without GitHub associates later by creating one new repository and pushing the custom addons already on the instance (`OdooGit::associateNewRepository`), not by picking an existing empty repository.

Not installed: create the app, then send them to install repositories (`getInstallationPath`). Do not stop on the Coolify page that only shows the button. After GitHub returns, create the Odoo service if it is missing and open the same new-vs-existing choice. Do not leave them on an empty resource index.

One repository per project (`owner/name` on the profile). It cannot belong to two projects. New repo slug is the project name (`Mi Empresa` → `mi-empresa`). Each environment stores its own `git_branch` in `odoo_environment_branches`. Two environments cannot share a branch. Without GitHub there is no branch row; the panel says JupyterLab.

Inside the project there is one list. A row is selected with one click. Clone and Open environment appear on that selection, not in the header. Clone is only there when the selection is production and it already has Odoo; the button says Clone. The choices open in a dialog, not a box above the list. While it runs, the screen says it is creating that staging and starting Odoo. Odoo projects stay Odoo-first in copy and shortcuts, but New resource and the empty-environment picker can launch any visible catalog service (platform without limits; Odoo is the hook, not the ceiling). Open environment opens the selected branch straight on the service panel (status, logs, actions), not the resource list. The gear on the environment name is that environment's settings. A member can open the environment and Odoo. If that branch has no service yet, the empty environment shows the catalog launch picker. While a launch is in progress, the service panel shows the loading steps. Do not redirect that panel back to the project.

Production is the environment, not a list of Compose services. Open Odoo from the project (`project.service.odoo.enter`). GitHub on `launch=choose` is the repository choice, not the mounted-service list. The public URL is `https://` without port `:8069` and opens the admin session at `/_odoo/paas/connect`. When the project subdomain and the Settings → Odoo base domain are both set, that host is `{subdomain}.{base domain}` for production and `{subdomain}-{environment}-{id}.{base domain}` otherwise. Saving a subdomain that changes the address restarts that Odoo service (`startIfPossible`) so Traefik and SSL apply. Workers alone wait for the next start. An empty subdomain writes the Coolify host back when the current host is under the base domain and restarts the same way. Odoo starts with `--proxy-mode` and `--no-database-list`, filtered to its own database. Each start writes `web.base.url` as `https://` in Postgres. HTTPS redirect must still allow `/.well-known/acme-challenge/`. A new Odoo version is a template under Settings.

A push to the saved `git_branch` reclones addons and restarts only the Odoo container. Pull requests do nothing. No second webhook.

Launch is not done until the certificate is Let's Encrypt (not the Traefik default) and `https://host/web/login` is the Odoo login, not the auto-refresh page and not 503 / "no available server". Open Odoo stays hidden while the container is exited. While Odoo installs, the public URL shows a Spanish auto-refresh page. A client whose service runs on server id 0 may use that server even though the server row belongs to the instance team. Do not re-download the image (`pullLatestImages false`, `--pull never`). Do not re-enable the image healthcheck. Do not reintroduce `gpsh-enter`. Listen stays `0.0.0.0:8069`.

In the new-project wizard and on an empty environment (catalog Launch), ask where it runs. Local is server id 0, offered even when that server belongs to the instance team, and only when `canLaunchOnInstanceServer()`. Without that permission and with no other server, the only question is whether to create a server. With permission, also offer creating a new server. If servers already exist, ask which one and default `serverId` to the first. Read the flag from `team_user`, not a stale team list. Owners can always use server id 0.

## Phases 3–10 — do not drop these

These are already started. Do not rip them out. Do not extend them unless the current phase flow is blocked.

- 3. Production and staging are two environments, two services, separate domains, databases, filestores, and addon volumes. The existing webhook dispatches the matching branch. A push does not build an image when the addons Application exists. Statuses: `queued`, `in_progress`, `finished`, `failed`, `cancelled-by-user`.
- 4. Deploy history reuses that queue or the service deploy, with those same statuses.
- 5. `OdooBackup` is `complete` only when the database execution and the filestore volume execution are both `success`. Restore or clone of data without that pair is refused. Plan `backup_frequency` / `backup_retention_days` drive those schedules. Migration from Odoo.sh (dump + filestore + optional GitHub repo) is gated by `includes_migration` and runs through `OdooMigrate` / `MigrateOdooShJob`.
- 6. Project view for member and owner: domain, version, workers, addon path, Jupyter, last status. Not the raw Docker inventory. No new server screens.
- 7. Version on the profile, workers, addon path, Jupyter optional per environment. The 17–20 selector on the service already exists.
- 8. Audit log (user, action, project, environment, result, metadata, no secrets) and the notification channels that already exist.
- 9. API `/api/v1/projects/{uuid}/odoo` calls the same actions as the UI.
- 10. A member cannot create or change a server or S3. Staging does not write to production. Abilities `odoo.*` granted by the owner do not open servers or S3. A member or admin can open the Odoo shell of a service on their team. An admin's other terminals stay limited to instances they created or were assigned.

## Corrections that override an older phase sentence

- Clone copies the database and the filestore, then Odoo neutralize. Staging stays writable. Phase 1's "the clone copies nothing" is stale. The only `:ro` is the production filestore during the copy. After start succeeds, a later copy failure keeps the staging environment.
- The environment name and `git_branch` are different fields. The database name is the environment name, not `{project}_{branch}`.
- Do not find Postgres as `postgresql-{uuid}`. Match image or name `*postgres*`, or label `coolify.service.subType=database`. Odoo is image `odoo:` or a name containing `odoo` but not jupyter. Do not stop Jupyter. Filestore ownership comes from `docker exec` uid/gid on the source Odoo, not hardcoded `101:101`.
- Wait until Odoo and PostgreSQL are running before the HTTPS check. Client Jupyter, Grafana, Prometheus, and cAdvisor are not part of that wait.
- A clone stays on the loading screen until that Odoo container is running and `https://host/web/login` is the real login. The job then stores `config_hash` for the configuration it just applied, so "The latest configuration has not been applied" does not appear because of the clone itself.
- Open Odoo and Open Jupyter keep those names and open outside GPSH. An external-link icon is the signal. The generic Links menu is hidden on an Odoo service. Logs is an extra panel action and stays on the service logs screen, so it does not use that icon.
- Jupyter is not an iframe. Its URL carries the token and there is no anonymous session. Idle kernels and terminals are culled. `odoo-logs.sh` in the Jupyter folder tails `/workspace/addons/.gpsh/odoo.log`, which Odoo writes on start. JupyterLab stays on for every Odoo service, with or without GitHub (`jupyter_enabled` true on create and in `ensureLaunchAllowed`).
- Choosing Odoo in Terminal runs `odoo shell` for that branch's database (`--no-http`, so it does not bind 8069). The client Jupyter terminal opens that same shell through port 8079. PostgreSQL and the owner Jupyter stay on the container shell.
- Owner modules are the instance owner's house modules. Settings → Odoo stores `instance_settings.odoo_owner_repository` and `odoo_owner_branch`. Save clones that branch with the instance team's GitHub App, not a client's, into `/data/coolify/gpsh-owner-modules` and does not restart Odoo. The next start copies each module (a folder with a manifest, or the repo itself when its name is a module name) into `/usr/lib/python3/dist-packages/odoo/addons` and removes the old `/mnt/extra-addons` symlinks. The client addon folder and client Jupyter do not get that directory. The token stays out of the Odoo launch command. To put a package branch into a client's `{uuid}_odoo-extra-addons` volume, the instance owner opens that Odoo service → Owner package, picks a branch, and installs (`OdooGit::installOwnerPackageIntoService` saves `odoo_environment_branches.owner_package_branch` and dispatches `SyncOdooAddonsJob`). Volume sync order is always client `cloneIntoService`, then `reinstallOwnerPackageIntoService` (merge stamped in `.gpsh/owner-package-modules`, keeps client addons and `.git`), then one Odoo restart. The same reinstall runs inside `StartService` after the client clone so a start or webhook does not drop the package. Clients do not see that panel.
- Owner Jupyter is one container outside the client stacks, opened from the menu and from an Odoo service by an instance admin (`isInstanceAdmin()`). A client does not see it. The workspace is `/workspace/{team}/{project}/{environment}/` with `custom_addons`, `odoo`, and `files` (read-only). Root Team maps to the folder `owner` (so you see `owner/odoo/…` and `owner/pollo-campero/…`). A real client team keeps its name (`cliente-1/…`). House modules mount at `/workspace/owner-modules`, not under `owner`. A custom volume on another server is copied in when the owner Jupyter opens. The public Odoo port forwards websocket upgrades to Odoo, so the real-time bus stays connected. The top-level `volumes` key is omitted when there is nothing to declare. Its router leaves `/.well-known/acme-challenge/` on port 80 and asks Let's Encrypt for that host. The client Jupyter stays inside its environment and mounts that environment's extra-addons, not production's. Deleting an environment stays available while it is still loading. - Outgoing Odoo mail reuses Settings → Email (`instance_settings` SMTP). Do not add a mail gateway, a second SMTP table, or SMTP columns on the project. `OdooMail::mailEnvironmentLines` (`app/Domain/Odoo/OdooMail.php`) builds the lines. `OdooGit::mailEnvironmentLines` delegates, and `Service::saveComposeConfigs` writes them into that Odoo service's `.env`. Each start upserts one standard `ir.mail_server` named GPSH and sets `mail.default.from` to the global sender, unless `ir.config_parameter` `gpsh.own_mail` already stores that server's id. The choice is made when a message is sent. `gpsh_autoconnect` overrides `ir.mail_server._find_mail_server`: a stored id is one read, and if that server still exists and is active the send uses it. If it was deleted or deactivated, the same send looks for another active server; if none remains, GPSH is activated again. A newly configured server is picked up on the next send. `gpsh.mail_route` is `own` or `gpsh`, and `gpsh.mail_last` is `sent` or `failed`. Each change writes one `gpsh mail` line to the Odoo log. A neutralized database (`database.is_neutralized`) does not send, and the next start leaves every outgoing server inactive.

## Permissions

The invite form (`InviteLink`) is where the owner sets this, before Generate link. The user is attached to the team with those values already. Empty number means no limit. An admin who invites cannot grant servers.

Written for admin and member: `max_projects`, `max_environments`, `max_members`, `max_production_branches`, `max_staging_branches`, `max_services`.

Admin only: `github_app_id`, `can_add_servers`, `can_launch_on_instance_server`.

Member only: `odoo_abilities` (grantable list). A member stays without server flags even if the form sends them.

`can_add_servers`: `ServerPolicy::create` is `canAddServers()`. `can_launch_on_instance_server`: may launch on server id 0. Read the flag with a fresh `teams()` query (`User::teamFlag`), not the in-memory team list. `OdooGit::allowedLaunchServers()` must `find(0)` when that flag is on. Server id 0 is the instance server and is often not on the client's team.

Owners always can. Members never can, even if the column is true. Server update/delete and S3 create stay owner-only. `S3StoragePolicy` stays as it is. `Storage\Create` is mounted on every page: authorize on submit, not on mount.

Terminal (`canAccessTerminal` plus the resource check): members never open a server terminal. The instance owner can open any terminal. A member or admin can open the Odoo shell of a service on their team, including when that service runs on server id 0. An admin can open another terminal only for an instance they created (`created_by`) or that the owner assigned to them. Another admin on the same team does not inherit that other terminal. The websocket allowlist is every server that user can use, including server id 0 when a service of their team runs there (`host.docker.internal`). It is not only `currentTeam()->servers`.

Odoo stays the container process. Start as root only to `chown` `/var/lib/odoo` to the `odoo` user, then drop privileges. Do not pass `gpsh_autoconnect` with `--load`. Install it in that branch's database (`-i gpsh_autoconnect`) so `/_odoo/paas/connect` exists on staging as well as production. A copied branch gets its own `ODOO_DATABASE` and `ODOO_LOGIN_TOKEN`; it must not keep production's. The image healthcheck stays disabled. Listen stays `0.0.0.0:8069`. The terminal allowlist includes server id 0 and `host.docker.internal` when that user can use the server, including when the service points at it through its destination.
